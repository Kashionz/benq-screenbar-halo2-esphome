# HaloDesk 跟隨電腦狀態規劃

狀態：規劃中，尚未實作。本文件只描述預定行為；實機結果待實作後記錄於 [開發驗收紀錄](DEVELOPMENT_ACCEPTANCE.md)。

## 目標

電腦離開使用狀態（鎖定、螢幕關閉、睡眠、關機）時自動關燈，使用者回來（解鎖、螢幕亮起、登入）時把 HaloDesk 關掉的燈開回來。Windows 與 macOS 行為一致：平臺差異只在 Rust 端的事件來源，判斷規則寫成一份共用、可單元測試的狀態機。

只控制電源：關燈送 `power=false`，開燈送 `power=true`，不改模式、亮度與色溫（掛燈開燈後沿用自己的設定）。掛燈的「入席偵測」開啟時本功能整個暫停，由掛燈自己依人是否在座開關燈，兩者不會同時控制電源（見「與入席偵測」）。

本功能需要 App 持續執行且保持連線。沿用已實作的開機自動啟動（`--autostart` 背景啟動、以已保存連線自動連線、單一執行個體，見 `app/README.md`「開機自動啟動」），另外新增一項 App 整體設定：關閉主視窗時要結束 App 還是隱藏到系統匣，由使用者選擇。

不列入本規劃：iOS（App 在背景不執行，也收不到這些系統事件）、Linux（第一版目標外，見「平臺」）、App 自訂閒置計時、依時段或排程開關、回來時套用情境、App 未執行時的控制（需要由橋接器或 Home Assistant 端的自動化負責）。

## 電腦狀態

各平臺事件先轉成三種電腦狀態，再交給共用狀態機：

| 狀態 | 意義 | 進入條件 |
| --- | --- | --- |
| 使用中 | 使用者在電腦前 | 已解鎖、螢幕開啟（含變暗）、未睡眠 |
| 離開 | 電腦開著但沒人用 | 鎖定、登出或切換使用者、所有螢幕關閉（含閒置後系統關螢幕） |
| 即將停止 | 即將睡眠、休眠、關機或重新啟動 | 系統送出睡眠／關機通知，尚未真正停止 |

- 「螢幕關閉」直接使用作業系統的螢幕電源狀態，閒置時間依系統的電源設定；播放影片等程式要求螢幕常亮時系統不會關螢幕，燈也不會被關。App 不另外計算閒置時間。
- 喚醒本身不算回到「使用中」。Windows Modern Standby 與 macOS Power Nap 會在無人時短暫喚醒做背景工作，這時螢幕不亮或停在鎖定畫面；要等到解鎖（沒有設定鎖定時為螢幕開啟）才算使用者回來。
- 使用者自己選「結束 HaloDesk」或關閉主視窗不屬於任何狀態，照舊不改變掛燈。

## 設定頁

既有的「啟動」分頁（目前只有「開機時自動啟動」）增加一項，另新增「跟隨電腦」分頁；兩者都只在 Windows 與 macOS 桌面 App 出現。

「啟動」分頁新增：

| 設定 | 選項 | 預設 |
| --- | --- | --- |
| 關閉主視窗時 | 結束 HaloDesk／隱藏到系統匣（macOS 為選單列） | 結束 HaloDesk（與現在相同） |

- 選「隱藏」時，關閉主視窗只把它藏起來，從系統匣面板、右鍵選單的「開啟 HaloDesk」或再次啟動 App（單一執行個體會顯示既有視窗）再打開；只有「結束 HaloDesk」才退出 App。
- 「跟隨電腦」有任一項開啟、但「關閉主視窗時」是「結束」或「開機時自動啟動」沒開時，「跟隨電腦」分頁頂部提示：關掉主視窗或重新開機後本功能不會動作，並提供跳到「啟動」的連結。不自動替使用者改設定。

「跟隨電腦」全部預設關閉：

| 設定 | 選項 | 預設 |
| --- | --- | --- |
| 離開時關燈 | 開／關；再分「鎖定或切換使用者」「螢幕關閉」兩個勾選 | 關 |
| 睡眠或關機時關燈 | 開／關 | 關 |
| 關燈前等待 | 0／10／30／60 秒，只用於「離開」 | 10 秒 |
| 回來時 | 不動作／只開回 HaloDesk 關掉的燈／一律開燈 | 只開回 HaloDesk 關掉的燈 |

- 「關燈前等待」：離開狀態要持續到時間結束才關燈，期間回到使用中就取消。鎖定後馬上解鎖、螢幕短暫關閉都不會關燈。睡眠與關機不等待。
- 「一律開燈」：回到使用中時燈是關的就送開燈，不論是誰關的。仍只在狀態轉換那一刻判斷一次，之後使用者自己關燈不會再被開回。
- 掛燈的入席偵測開啟時，分頁頂部顯示「入席偵測開啟中，跟隨電腦暫停」，設定仍可修改。
- 分頁底部顯示最近一次自動動作，例如「睡眠時關燈 · 已送出 · 23:41」「回來時未開燈：燈已被其他來源變更」或「鎖定時未關燈：入席偵測開啟中」，方便使用者理解為什麼燈沒有動。
- 設定保存在 App 資料目錄（`system-follow.json`，原子寫入）。檔案損壞時顯示錯誤、保留原檔並停用本功能，不以預設值覆蓋。

## 只開回自己關掉的燈

HaloDesk 每次因電腦狀態送出關燈且結果為已送出，就記一筆「自動關燈紀錄」：橋接器 device_id、boot_id、command_id、觸發原因與時間。回到使用中時，下列條件全部符合才送開燈：

1. 有自動關燈紀錄，且 device_id 與目前連線相同。
2. 目前目標電源是關。
3. 目前目標仍是那筆命令設定的：boot_id 相同，且 `desired.command_id` 等於紀錄的 command_id。
4. 入席偵測沒有開啟。

條件 3 確保期間若有人用原廠控制器、網頁、Home Assistant 或另一台電腦改過燈（包括切換入席偵測），HaloDesk 不會蓋掉；橋接器重新開機後同樣不開燈。不論最後是否送出，紀錄都在這次判斷後清除，一筆紀錄最多換來一次開燈。

紀錄與設定存在同一個檔案，讓「關機時關燈 → 下次登入開回」也能運作；檔案不含帳密、IP 或主機名稱。

## 與入席偵測

掛燈的入席偵測（協定欄位 `ultrasonic_enabled`）由掛燈自己的超音波感測器判斷人是否在座並開關燈，橋接器收不到它造成的開關。它和本功能都是「人離開就關、回來就開」，兩者同時控制電源會互相打架，例如：

- 人在座位上看紙本、電腦閒置關了螢幕：入席偵測認為有人要亮燈，本功能卻送出關燈。
- 人離開後掛燈已自行熄燈、電腦接著鎖定：本功能送出關燈，掛燈被切成真正的「關」，使用者坐回來時入席偵測可能不會再把燈點亮（未實測），要等解鎖才亮。

因此一律以掛燈的入席偵測優先，本功能只在入席偵測關閉時運作：

1. 每次要送命令前，協調器都會讀一次最新狀態（見「執行架構」）。目標的 `ultrasonic_enabled` 為開時不送任何命令，不論觸發是離開、睡眠、關機或回來，並記錄「入席偵測開啟中」。
2. 判斷用送出前那一刻的狀態，不用觸發當時的狀態。「關燈前等待」期間使用者打開入席偵測，等待結束時也不會關燈。
3. 入席偵測開啟時，未使用的自動關燈紀錄在下次回到使用中時清除、不開燈（「只開回」條件 4）。之後再關閉入席偵測，也不會補開。
4. 本功能不會為了自己能運作而送命令關閉入席偵測，也不會在回來時把它打開。要讓 HaloDesk 跟隨電腦，使用者需自行在主視窗關閉入席偵測。
5. 判斷依據是橋接器的目標值。使用者以原廠控制器切換入席偵測、而橋接器沒收到那筆封包時，目標值會與掛燈不一致；這屬於現有的接收限制，本功能不另外偵測。橋接器回報此欄位為 unsupported 時，視為入席偵測未開啟。

## 執行架構

```text
Windows / macOS 系統事件        src-tauri/src/system/{windows,macos}.rs
        ↓ 正規化成「使用中／離開／即將停止」
共用狀態機（純邏輯）             app-support/src/system_follow.rs
        ↓ 關燈／開燈／不動作
系統協調器                       src-tauri/src/system/mod.rs
        ↓ 共用既有 Session 與 Bridge 命令規則
橋接器；結果以 halo-system-command 事件通知主視窗
```

與系統匣、[外部控制](EXTERNAL_CONTROL_PLAN.md)不同，系統觸發由 Rust 直接送命令，不經主視窗：

- 睡眠與關機只留很短的時間（Windows 睡眠約 2 秒），命令必須在系統通知回傳前送完；隱藏中的 WebView 可能被節流（例如 macOS App Nap），無法保證及時處理事件。
- `Bridge` 已在 Rust 端強制關鍵規則：結果不明時拒絕新寫入、命令間隔 500 ms、無線模組未就緒或裝置忙碌時拒絕、每筆命令前讀取新的 boot／revision。系統協調器沿用這些規則，不另做一套。

協調器規則：

1. 只在已連線時動作。未連線、離線、無線模組未就緒、上一筆結果不明時直接放棄，不排隊、不等連線恢復後補送。
2. 使用者的命令正在傳送時，可在期限內等待 Session 鎖；剛送過命令時等 500 ms 間隔結束再送。等待只發生在送出前，每次觸發最多一筆 POST，送出後不重試。
3. 入席偵測開啟中、燈已是目標狀態，或不符合「只開回」條件時就不送。這些條件用 `Bridge::set_state` 送出前本來就會讀的那份狀態判斷：`bridge-core` 增加一個帶前提檢查的送出方法，讀到狀態後先檢查、不符合就直接回傳「略過」不發 POST。不另外多讀一次，省下睡眠期限內的一次往返，也避免兩次讀取之間狀態改變。此變更不影響 wire protocol。
4. 結果以 `halo-system-command` 事件送主視窗。主視窗照處理自己命令結果的方式更新畫面：結果不明時鎖定並提供「查詢命令結果」，並丟棄尚未送出的燈光調整。系統匣面板跟著主視窗更新。
5. 回到使用中時，若上一筆系統命令結果不明，先以原 command_id／boot_id 查詢一次（GET，不重送）。查得已送出才繼續判斷是否開燈；仍不明就不動作，留給使用者在主視窗查詢。
6. 每筆命令照常寫入診斷紀錄，另記觸發原因（鎖定、螢幕關閉、睡眠、關機、回來、登入），不含自由文字。

## 時間限制

| 情況 | 可用時間 | 做法 |
| --- | --- | --- |
| 離開（鎖定、螢幕關閉） | 不限 | 等設定的秒數後送出 |
| Windows 睡眠、休眠 | 約 2 秒 | 在 `PBT_APMSUSPEND` 回呼內同步送出，期限 1.5 秒 |
| macOS 睡眠 | 系統最多等 30 秒 | 收到 `kIOMessageSystemWillSleep` 後送完或 5 秒期限到，才呼叫 `IOAllowPowerChange` |
| Windows 關機、重新啟動、登出 | 約 5 秒後系統顯示「程式阻止關機」 | 在 `WM_QUERYENDSESSION` 內以 `ShutdownBlockReasonCreate` 顯示原因並同步送出，期限 3 秒 |
| macOS 關機、重新啟動、登出 | 待實測 | 在 `NSWorkspaceWillPowerOffNotification` 內送出，期限 3 秒 |
| 回來（解鎖、喚醒後亮螢幕、登入） | 網路可能尚未恢復 | 每 2 秒唯讀讀取狀態，最多 30 秒；讀到後才判斷，最多送一筆 |

- 期限到時不論命令進行到哪裡都讓系統繼續。若 POST 已送出但沒收到回應，就是一般的「結果不明」，回來時依協調器規則 5 查詢原命令。
- 多數設定是先鎖定或關螢幕、之後才睡眠，所以燈通常在睡眠前已因「離開」關掉，睡眠時不需要再送。
- 一般區網一筆命令（讀狀態＋POST＋查結果）約數百毫秒；最差情況受 4 秒 HTTP 逾時限制，會超過睡眠期限。實際延遲列入實測。
- 關機與重新啟動無法可靠區分，重新啟動也會關燈，登入後再依「回來時」設定開回。

## 啟動與連線

系統協調器需要已登入的連線，HaloDesk 沒在執行時本功能不會動作。

已實作、本功能直接沿用的部分（見 `app/README.md`「開機自動啟動」）：

- 「設定 → 啟動」的「開機時自動啟動」以 `tauri-plugin-autostart` 註冊（Windows 為目前使用者的 `Run`，macOS 為 LaunchAgent），登入時帶 `--autostart` 在背景啟動，主視窗隱藏、只留系統匣或選單列圖示。
- 這種啟動若有已保存的連線，會自動連線一次（只有 GET，不送燈光命令）；失敗時，下次開啟系統匣面板再試；按「中斷連線」後不再自動連線。手動開啟 App 不自動連線。
- 單一執行個體：背景執行時再開啟 HaloDesk，會顯示既有的主視窗。

本功能新增：

- **登入初期重試**：「跟隨電腦」有任一項開啟時，`--autostart` 啟動的自動連線遇到網路錯誤，改為每 5 秒再試一次、最多 60 秒（登入當下網路常尚未就緒），不必等使用者開啟系統匣面板；60 秒後仍失敗，就回到現有的「開啟面板時再試」。認證失敗、裝置識別改變時立即停止。這些都是 GET，不涉及 RF 命令。
- **登入開回**：`--autostart` 啟動後第一次連線成功（不論是第一次嘗試、重試或開啟面板時連上），若「跟隨電腦」有開啟，視為一次「回到使用中」，套用「回來時」設定。搭配關機時的自動關燈紀錄，就是「關機關燈、登入開回」。手動開啟 App 後的連線不觸發。
- **關閉主視窗**：依「啟動」分頁的「關閉主視窗時」設定。選「隱藏」時攔下關閉事件改為隱藏視窗（取代現在 `main` 視窗 `Destroyed` 就結束 App 的處理），主視窗與 WebView 都保留，系統匣面板與右鍵選單照常可用；隱藏期間主視窗照現在的規則停止 2 秒輪詢，重新顯示時同步一次狀態。macOS 隱藏時是否一併隱藏 Dock 圖示列入實測。

## 平臺

| 項目 | Windows | macOS |
| --- | --- | --- |
| 鎖定、解鎖 | `WTSRegisterSessionNotification` → `WM_WTSSESSION_CHANGE`（LOCK／UNLOCK、LOGOFF、快速切換使用者的 CONSOLE_DISCONNECT／CONNECT） | `com.apple.screenIsLocked`／`com.apple.screenIsUnlocked` 分散式通知（非正式 API）；快速切換使用者用 `NSWorkspaceSessionDidResignActive`／`DidBecomeActive` |
| 螢幕 | `PowerSettingRegisterNotification(GUID_CONSOLE_DISPLAY_STATE)`：0 關、1 開、2 變暗 | `NSWorkspaceScreensDidSleep`／`ScreensDidWake` |
| 睡眠、喚醒 | `PowerRegisterSuspendResumeNotification`（`PBT_APMSUSPEND`、`PBT_APMRESUMESUSPEND`、`PBT_APMRESUMEAUTOMATIC`） | `IORegisterForSystemPower`（`kIOMessageSystemWillSleep`、`kIOMessageSystemHasPoweredOn`；`kIOMessageCanSystemSleep` 直接允許，不阻止閒置睡眠） |
| 關機 | 隱藏頂層視窗收 `WM_QUERYENDSESSION`／`WM_ENDSESSION` | `NSWorkspaceWillPowerOffNotification` |
| 登入啟動 | 已實作：`tauri-plugin-autostart`（`HKCU\…\Run`） | 已實作：`tauri-plugin-autostart`（LaunchAgent） |
| 依賴 | 既有 `windows` crate 增加所需 features | `objc2`、`objc2-app-kit`、`objc2-foundation` 與 IOKit FFI |

- Windows 監聽放在專用執行緒，建立自己的隱藏頂層視窗與訊息迴圈（message-only 視窗收不到關機廣播），不掛在 Tauri 主視窗上；回呼內的同步等待不會卡住 UI 執行緒。
- macOS 的 IOKit 通知放在專用執行緒的 CFRunLoop，命令完成後才呼叫 `IOAllowPowerChange`，不阻塞主執行緒。背景執行時 App Nap 是否延遲「關燈前等待」計時與喚醒後讀取，列入實測，必要時以 `NSProcessInfo` activity 排除。
- 鎖定通知是 macOS 的非正式 API；若在目標版本失效，鎖定改由「螢幕關閉」涵蓋，設定頁的「鎖定」勾選在 macOS 上停用並說明。
- Linux 不在第一版目標。狀態機與平臺層分開，日後可用 systemd-logind D-Bus（`PrepareForSleep` 搭配 delay inhibitor、Session 的 `Lock`／`Unlock`）接入。
- iOS 不編譯此模組。

## 安全與限制

- 只送電源開／關。前端只能讀寫「跟隨電腦」設定（`system_follow_settings`、`set_system_follow_settings`），不能指定任何動作；新命令只授予主視窗，系統匣面板的 capability 不變。
- 不重送：每次觸發最多一筆 POST。失敗或結果不明不補送；回到使用中也不補送離開時沒送成功的關燈。
- 不修正：之後原廠控制器、網頁、Home Assistant 或其他電腦改了燈，HaloDesk 不會送命令改回；只在狀態轉換那一刻判斷一次。
- 多台電腦都開啟本功能時，各自只開回自己關掉的燈（command_id 不同）；選「一律開燈」時，任一台回到使用中都會開燈。
- 入席偵測開啟時不送任何命令，也不替使用者切換入席偵測（見「與入席偵測」）。
- `transmitted` 只代表橋接器已送出，介面與文件寫「已送出關燈」，不寫「燈已關」。

## 實作順序

1. **關閉主視窗**：「啟動」分頁的「關閉主視窗時」與隱藏行為。不依賴本功能，可先單獨交付；測試涵蓋設定讀寫、隱藏後由系統匣與再次啟動重新開啟、選「結束」時行為與現在相同。
2. **狀態機**：`app-support/src/system_follow.rs`，輸入電腦事件、設定、時間與自動關燈紀錄，輸出動作。放在 `app-support` 讓 CI 的 `cargo test -p halo2-app-support` 涵蓋。單元測試：等待期間回來取消、鎖定後立即解鎖、喚醒後停在鎖定畫面不開燈、紀錄只用一次、設定檔損壞。
3. **前提檢查送出**：`bridge-core` 增加帶前提檢查的送出方法。測試：入席偵測開啟時離開、睡眠、關機、回來都略過且不發 POST；等待期間開啟入席偵測後不關燈；只開回條件（device_id、boot_id、command_id 不符、燈已開、入席偵測開啟）各自略過；結果不明時拒絕；unsupported 欄位視為未開啟。
4. **設定與紀錄檔**：`system-follow.json` 讀寫（原子寫入）、Tauri commands 與 capability。
5. **協調器**：Session 鎖等待期限、500 ms 間隔、結果不明時的查詢、`halo-system-command` 事件與診斷觸發原因；主視窗處理事件（顯示結果、結果不明時鎖定、丟棄未送出的調整）。以模擬事件測試，不需真的讓電腦睡眠。
6. **Windows 監聽**：session、螢幕、睡眠、關機。
7. **「跟隨電腦」分頁**：設定、入席偵測暫停提示、關閉主視窗與登入啟動的提示、最近一次自動動作、中英文字串。
8. **登入流程**：在既有的 `--autostart` 自動連線上加入登入初期重試與「登入開回」；前端測試涵蓋重試期間連上、60 秒後放棄、認證失敗不重試、中斷連線後不再重試、手動開啟不觸發。
9. **macOS 監聽**：CI 建置通過；實機另行驗收。
10. **文件與驗收**：更新 `app/README.md`。Windows 實際操作鎖定、關螢幕、睡眠、關機與重新啟動（傳統 S3 與 Modern Standby 各一台為佳），人工確認掛燈變化，記錄每種情況從事件到送出的延遲；另在入席偵測開啟下重複一次，確認沒有送出命令、掛燈照入席偵測開關。結果寫入 `docs/DEVELOPMENT_ACCEPTANCE.md`。macOS 另行驗收。

每一步都需通過 `app/` 既有檢查（`npm test`、`cargo test`、`cargo clippy -D warnings`、`cargo fmt --check`、debug 建置）。

## 待實測確認

- Windows Modern Standby 電腦上，螢幕關閉與睡眠通知的先後，以及睡眠通知當下網路是否仍通。
- Windows 睡眠回呼約 2 秒內能否完成一筆命令；關機時 `ShutdownBlockReasonCreate` 期間能否送完。
- macOS 鎖定通知在目標版本是否仍送出；關機通知後實際可用時間；App Nap 對背景計時的影響。
- 喚醒後網路恢復所需時間，30 秒讀取期限是否足夠。
- 以原廠控制器切換入席偵測後，橋接器的 `ultrasonic_enabled` 目標值是否每次都跟著改變（本功能的暫停判斷依賴它）。
- macOS 主視窗隱藏時是否一併隱藏 Dock 圖示。
- 快速切換使用者與遠端桌面連線時收到的事件。
